The data contract

Bad rows never reach the live tables. They're quarantined, with a reason.

rulelive, 4 Nov
bogus_timestamp · before Citi Bike existed48
over_capacity · bikes + docks > capacity + 29–15
future_timestamp · unknown_station · duplicate_station0
invalid_count · ebikes_exceed_bikes · invalid_flag0
outside_service_area · missing_name · invalid_capacity0

Postgres CHECK constraints repeat the critical rules. Every run, even a failed one, writes an ingest_runs row, so a silent pipeline shows up as stale data.

Built for Sodabase

Designed so "normal" is easy to learn, and a problem is easy to see.

STALE

A heartbeat every minute

ingest_runs and system_pulse insert one row a minute; ~1,800 stations re-report in station_status. A stopped cron shows within minutes.

EMPTY

Nothing is ever deleted

History is insert-only; live tables are upserted in place. No truncation, so a row-count drop is always a real problem.

WRONG

Contract + constraints

Schema only changes through migrations. Bad values are blocked twice: in TypeScript, then by Postgres.

Sodabase closes the loop. Every answer calls Sodabase's MCP check_trust on public.station_status. If Sodabase says untrusted, Spoke won't answer, however healthy its own pipeline looks.
